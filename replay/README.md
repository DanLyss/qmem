# qmem-replay: что сделано в итерации 1

2026-10-12 · план и устройство: [docs/modules/replay.md](../docs/modules/replay.md)

Replay воспроизводит нагрузку приложения на память без самого приложения. Цикл замкнут: запись оригинала → profile → replay → запись replay → сравнение. Всё проверено под root с настоящим DAMON на WSL2 (ядро 6.18, damo 3.3.0). В этой итерации только анонимная память и один поток.

## Что лежит в репозитории

| Файл | Что это |
| --- | --- |
| `replay/replay.c` → `qmem-replay` | Воспроизведение profile (C, без зависимостей) |
| `tools/mkprofile.py` | profile из каталога записи `qmem-record` |
| `tools/compare.py` | Сравнение записи оригинала и записи replay |
| `examples/python_phases/cycle/` | Пример полного цикла с результатом сравнения |
| `tests/test_replay.py`, `test_mkprofile.py`, `test_compare.py`, `test_replay_e2e.py` | Тесты |

Сборка: `make`.

## Как пользоваться

```sh
sudo record/qmem-record.sh -o orig -w 2000 -- ./my_app        # записать оригинал
tools/mkprofile.py orig -o profile.txt                        # построить profile
sudo record/qmem-record.sh -o again -w 2000 -- replay/qmem-replay profile.txt
tools/compare.py orig again --check                           # насколько похоже
```

`qmem-replay <profile.txt> [--seed N] [--stats <file>]` можно запускать и без записи. Root ему не нужен. В конце он печатает сводку в stderr: план и сделанные касания, отставание, page faults, пиковый RSS, CPU.

## Формат profile

Текст, одна запись на строку:

```
qmem-profile 1
epoch_ms 100
seed 42
region 2 318033920                    # id, размер
map 1502 2 0 315801600                # t_ms, region, offset, len
populate 1502 2 0 315801600           # записать каждую страницу один раз
epoch 3000                            # начало эпохи
access 2 284168192 32935936 1527790 1.0   # region, offset, len, касаний/с, доля записи
unmap 6879 2 0 201326592
```

Как устроен replay и откуда mkprofile берёт каждое поле — в [docs/modules/replay.md](../docs/modules/replay.md).

## Насколько replay похож на оригинал

| Метрика | `hot_region 256 16 8` | `examples/python_phases` |
| --- | --- | --- |
| Пиковый RSS | +0.1% | +0.3% |
| Память с обращениями (DAMON) | +0.6…+11% | −4.5% |
| Память с частотой >50% | ±2% | +1.1% |
| Page faults приложения | −4…−5% | +0.6% |
| Доля записанных страниц | ±5% | −70%, артефакт soft-dirty (ниже) |

Сам replay: около 8% одного ядра, ~1.5 МБ своей памяти.

## Что нашли и исправили по ходу

| Проблема | Исправление |
| --- | --- |
| Резидентная, но холодная память не воспроизводилась: 75 МБ RSS вместо 303 МБ | Событие `populate` по росту Rss в smaps |
| Случайный выбор страниц оставлял ~1/e участка нетронутым, DAMON видел replay холоднее | Обход участка по кругу |
| Касания тиками по 10 мс шли всплеском, половина проверок DAMON попадала на паузу | Тики по 1 мс |
| `ru_maxrss` показывал память процесса-родителя | Пиковый RSS из `VmHWM` |

Сквозной цикл нашёл и баги в record, они исправлены там же:
- приложение путалось с короткоживущим вспомогательным процессом damo;
- падение при исчезнувшем процессе;
- потерянный код выхода damo;
- в `system.csv` не видно faults приложения до первого снимка — добавлен `proc.csv`.

## Ограничения и что дальше

- **Только анонимная память.** Отображения файлов mkprofile пропускает и печатает их число.
- **Soft-dirty завышает запись после munmap или mremap посреди VMA.** Ядро помечает такую VMA целиком; решение — флаг `sd` из smaps.
- **Какие именно страницы резидентны, неизвестно.** `populate` берёт младшие адреса.
- **Один поток.** Давление на память задаётся снаружи (`systemd-run -p MemoryMax=...`).
- **Время старта.** Оригинал успевает выделить память до первого снимка, replay делает это в момент снимка; compare выравнивает записи по росту RSS.
