# Пример записи: Python-скрипт с тремя фазами

2026-10-09 · WSL2, ядро 6.18, damo 3.3.0, root

Настоящая запись `qmem-record` для [demo_app.py](demo_app.py). Скрипт работает около 9 секунд:

1. через 1 с после старта выделяет 300 МБ (300 `bytearray` по 1 МБ);
2. четыре секунды пишет в первые 30 МБ и трогает по паре байт в каждом мегабайте следующих 100 МБ;
3. освобождает 200 МБ, читает файл и через 2 с завершается.

Как записано:

```sh
sudo record/qmem-record.sh -o record -i 500 -w 2000 -- python3 demo_app.py
```

Сводка: `tools/summarize-record.py examples/python_phases/record`.

## Что видно в записи

| Время | Фаза | `system.csv` | smaps | `access.csv` (DAMON) | `writes.csv` | `syscalls.txt` |
| --- | --- | --- | --- | --- | --- | --- |
| 0–1 с | старт | MemFree 4935 МБ | anon 1.6 МБ | обращений почти нет | — | — |
| ~1.2 с | выделение | MemFree −310 МБ, pgfault +83 тыс. | anon 303 МБ | под наблюдением 520 МБ | VMA 303 МБ, грязных 303 МБ | 300 × `mmap(len: 0x101000)` |
| 2–6 с | работа | без изменений | anon 303 МБ | горячий регион 29.9 МБ, частота 100% | грязных 30.1 МБ из 303 | ничего |
| ~6.4 с | освобождение | MemFree +192 МБ | anon 111 МБ | под наблюдением 420 МБ | VMA 110 МБ | 200 × `munmap` |
| ~8.4 с | выход | | | | | ещё 100 × `munmap` |

- **Источники совпадают по времени.** Первый `mmap` в трассе — через 1.17 с после старта записи: это `sleep(1)` плюс импорт Python.
- **DAMON и soft-dirty дополняют друг друга.** DAMON видит горячие 30 МБ, soft-dirty показывает, что в этот участок писали.
- **pid в namespace.** `pid` 91431 — так приложение видно в WSL, `kernel_pid` 27697 — так его видит ядро; события в трассе идут с ним.

## Чего здесь нет, и почему

- **Чтение 100 МБ.** Скрипт трогает только около 100 страниц на 100 МБ, и для DAMON это не горячий участок. Это особенность демо, а не ошибка записи.
- **`brk`.** Python выделил кучу при старте, до включения трассировки: первые доли секунды в запись не попадают.
- **Чтение файла.** Файл маленький (6 МБ) и уже лежал в кэше, поэтому pgmajfault не изменился.

В `meta.json` команда записана с путём к временному каталогу, где запись делалась.

## Сквозной цикл: запись → profile → replay → запись → сравнение

2026-10-12 · каталог [cycle/](cycle)

```sh
sudo record/qmem-record.sh -o cycle/orig -i 500 -w 2000 -- python3 examples/python_phases/demo_app.py
tools/mkprofile.py cycle/orig -o cycle/profile.txt
sudo record/qmem-record.sh -o cycle/again -i 500 -w 2000 -- replay/qmem-replay cycle/profile.txt
tools/compare.py cycle/orig cycle/again --check
```

`cycle/orig` — новая запись того же скрипта (уже с `proc.csv`), `cycle/profile.txt` — 347 строк, 8 регионов, 77 эпох.

| Метрика | Оригинал | Replay | Расхождение |
| --- | --- | --- | --- |
| Пиковый RSS анонимной памяти, МБ | 303.7 | 304.8 | +0.3% |
| Память с обращениями (DAMON), МБ в среднем | 21.4 | 20.4 | −4.5% |
| Память с частотой >50%, МБ в среднем | 18.1 | 18.3 | +1.1% |
| Page faults приложения | 95 872 | 96 400 | +0.6% |
| Page faults системы | 160 177 | 162 507 | +1.5% |
| Доля записанных страниц | 0.323 | 0.098 | −70% |

`--check` (допуск 20% по RSS, памяти с обращениями и faults приложения) проходит.

Доля записи расходится не из-за replay. Когда Python освобождает 200 МБ из середины отображения, ядро помечает получившуюся VMA флагом `VM_SOFTDIRTY`, и pagemap показывает грязными все её страницы. В записи оригинала так «записанными» оказались оставшиеся 109 МБ (замер на 6.3 с). Подробно — в [docs/modules/replay.md](../../docs/modules/replay.md).

Сам replay ([cycle/replay_summary.txt](cycle/replay_summary.txt)): 0.63 с CPU за 8.3 с, то есть около 8% одного ядра; заполнение 300 МБ при старте задерживает расписание на 124 мс.
