# Один полный цикл: record → mkprofile → replay → verify

2026-10-12 · WSL2, ядро 6.18, damo 3.3.0, root

Весь пайплайн одной командой:

```sh
sudo verify/cycle.sh -o examples/cycle_demo -i 250 -w 2000 -- python3 examples/python_phases/demo_app.py
```

Что пишет приложение ([demo_app.py](../python_phases/demo_app.py), ~8 с):

1. через 1 с выделяет 300 МБ (300 `bytearray` по 1 МБ);
2. 4 с пишет в 30 МБ из них и читает по паре байт из ещё 100 МБ;
3. освобождает 200 МБ, читает файл, ждёт 2 с и завершается.

Итог: **verify прошёл** (`cycle.sh` вернул 0).

## Что делает цикл и какие файлы получаются

| Шаг | Команда внутри `cycle.sh` | Результат |
| --- | --- | --- |
| 1. Запись оригинала | `record/qmem-record.sh -o orig -i 250 -w 2000 -- python3 demo_app.py` | `orig/` |
| 2. Profile | `tools/mkprofile.py orig -o profile.txt` | `profile.txt` |
| 3. Запись replay | `record/qmem-record.sh -o again ... -- replay/qmem-replay profile.txt --layout layout.txt` | `again/`, `layout.txt` |
| 4. Сравнение | `verify/qmem-verify.py orig again --profile profile.txt --layout layout.txt --check` | `verify.txt`, `verify.json` |

`orig/` и `again/` устроены одинаково: replay записывается тем же `qmem-record`, что и оригинал.

## orig/ и again/ — записи

| Файл | Что в нём | Пример из `orig/` |
| --- | --- | --- |
| `meta.json` | Паспорт записи: команда, pid (в WSL и в ядре), интервалы, причина остановки, время, паузы VM | `"stop_reason": "exited"`, `"paused_ms": 0` |
| `access.csv` | **Главное.** Регионы памяти по DAMON и частота обращений к ним, снимок каждые ~100 мс. Колонки: время снимка (нс от старта записи), адреса региона, `access_rate` (% проверок DAMON, в которых регион трогали), `access_hz`, `age` | 1752 строки, 77 снимков |
| `smaps/<ts_ms>.txt` | Копия `/proc/<pid>/smaps` раз в 250 мс: какие отображения есть, анонимные или файл, сколько резидентно (Rss) | 28 снимков |
| `proc.csv` | Счётчики самого приложения: page faults (с его старта) и RSS | `359,1243,0,10344` |
| `system.csv` | Память всей системы: MemFree, Cached, PSI, pgfault, swap | — |
| `writes.csv` | Раз в 2 с (`-w 2000`) по каждому отображению: страниц в памяти, записано за период, из них перезаписано (лишние faults от самого замера) | на 4.4 с: 77489 в памяти, записано 7717 (30 МБ) |
| `syscalls.txt` | Сырой лог tracefs: mmap/munmap/brk/madvise приложения | 300 × `mmap(len: 0x101000)` — 300 bytearray по 1 МБ |
| `clock.csv` | Служебный: метки для перевода времени DAMON в время записи | — |
| `pauses.csv` | Паузы виртуальной машины (здесь их не было) | пусто |
| `damon.data`, `damon.data.kdamonds` | Внутренние файлы damo; напрямую не читаются | — |

Время во всех файлах отсчитывается от старта своей записи.

## profile.txt — сценарий для replay

Его строит mkprofile из `orig/`. 69 строк `epoch`, 8 регионов.

```
region 2 317898752 0x74b7dfad4000   # регион 2: 303 МБ, в оригинале по этому адресу
map 1220 2 0 315801600              # на 1220 мс выделить 301 МБ региона 2
populate 1220 2 0 315801600         # и сразу записать каждую страницу (так делает Python)
epoch 3000                          # эпоха 3000–3100 мс:
access 2 284168192 32935936 ...     #   трогать участок 271–302 МБ региона 2 с такой-то частотой
unmap 6331 2 0 105267200            # на 6331 мс освободить начало региона
```

Как читать:
- `region` — непрерывный участок адресов, где у приложения была анонимная память;
- `map`/`unmap`/`populate` — когда выделять, освобождать и заполнять. Это из снимков smaps: момент ставится посередине между двумя снимками, где увидели изменение;
- `epoch` + `access` — какие участки трогать в эту эпоху и сколько касаний страниц в секунду. Это из `access.csv`: частота DAMON переведена в касания. Пятое поле `access` — доля записи, она из `writes.csv`.

mkprofile пропустил 32 файловых отображения: библиотеки и сам python. Replay их не воспроизводит.

## layout.txt — где replay положил регионы

```
start_boottime_ns 34057326322074      # момент «времени 0» сценария
region 2 0x7dff970d3000 317898752     # регион 2 в этом прогоне replay
```

Нужен только verify: по нему адреса и время записи replay переводятся в те же координаты (регион + смещение + время сценария), что и у оригинала.

Сводка самого replay (печатается в stderr): все 68 эпох выполнены, 6.14 млн касаний из 6.15 млн запланированных, заполнено 77755 страниц, 0.59 с CPU за 8.5 с.

## verify.txt — результат сравнения

### 1. Частота обращений по месту — главная проверка

Обе записи переведены в «регион + смещение + время». Ячейки: 500 мс × 1/64 региона.

| Метрика | Значение | Порог | Как читать |
| --- | --- | --- | --- |
| `mae_pp` | 3.3 | ≤ 10 | В среднем частота в ячейке отличается на 3.3 процентных пункта |
| `corr` | 0.996 | ≥ 0.8 | Форма карты (где и когда горячо) совпадает |
| `hot_recall` | 1.0 | ≥ 0.8 | Всё, что было горячим (≥ 50%) у оригинала, есть и у replay |
| `hot_precision` | 1.0 | ≥ 0.8 | У replay нет горячего там, где у оригинала холодно |

Ниже в `verify.txt` — текстовые карты крупных регионов. Строка — 500 мс, столбец — 1/64 региона (для региона 2 это 4.7 МБ), цифра — частота / 10, слева оригинал, справа replay:

```
t=  3000 ...0000007999996 | ...0000007999995
t=  6000 ...0000005777774 | ...0000005777774
t=  6500 ...0000000000000 | ...0000000000000
```

Горячие 30 МБ (последние ~7 столбцов) в фазе 2 у обоих в одном месте и с одной частотой, в фазе 3 у обоих остывают. Точки `.` — в оригинале этой памяти в тот момент не было.

Мелкие регионы (куча, стек — десятки КБ) в таблице по регионам дают корреляцию около 0 или отрицательную. Это ожидаемо: там почти ничего не происходит, и корреляция между двумя почти пустыми картами ничего не значит. В общую оценку они идут с весом по объёму.

### 2. Во времени

| Метрика | Значение | Как читать |
| --- | --- | --- |
| `rss_mean_dev` | 0.10 | Ряд RSS replay в среднем отличается на 10% от пика оригинала (порог 0.2). Отличие в момент выделения 300 МБ: у оригинала оно размазано на ~100 мс, у replay приходится на одну эпоху |
| `minflt_mean_dev` | 0.08 | Ряд page faults приложения отличается в среднем на 8% |

### 3. Итоги

| Метрика | Оригинал | Replay | Как читать |
| --- | --- | --- | --- |
| `rss_peak_mb` | 303.7 | 304.8 | Пиковый RSS: +0.3% |
| `hot50_mb_mean` | 15.7 | 15.1 | Память с частотой > 50% внутри регионов: −3.8% (проверяется) |
| `hot_mb_mean` | 18.3 | 20.5 | То же с любой частотой > 0: +12% (справочно — тянется за короткоживущими регионами DAMON с низкой частотой) |
| `app_minflt_net` | 77998 | 78209 | Page faults приложения без тех, что вызвал сам замер soft-dirty: +0.3% (проверяется) |
| `app_minflt` | 103604 | 112569 | Без вычета: +8.7% — разница в числе сбросов soft-dirty, а не в работе |
| `dirty_share` | 0.096 | 0.161 | Доля записанных страниц, справочно. Завышена у replay: после освобождения части VMA ядро помечает её грязной целиком (в `writes.csv` на 8.4 с — 28048 из 28048) |
| `pgfault`, `pswpout`, ... | | | По всей системе; справочно |

`replay starts +166 ms later than the original` — сдвиг, на который verify выровнял записи.

### verify.json

Те же числа для автоматики, плюс `failed` (пусто — проверка пройдена), `gaps` и `pauses`.

## Как это трактовать

- **Что это значит.** Replay выделил и освободил ту же память в те же моменты и трогал те же участки с той частотой, какую видит DAMON. Пиковый RSS и page faults приложения совпали с точностью до долей процента.
- **Чего это не значит.** Это не совпадение каждого обращения. Сравнение идёт глазами DAMON, а он выборочный: одна страница региона раз в 5 мс, и profile построен по нему же. Нагрузка одна и простая, без нехватки памяти. Только анонимная память и один поток.
